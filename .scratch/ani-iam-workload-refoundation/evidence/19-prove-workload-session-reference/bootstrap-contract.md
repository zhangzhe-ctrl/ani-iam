# WR-19 Workload bootstrap implementation contract

This file freezes the independent bootstrap slice. The rest of WR-19 acceptance is unchanged and not yet verified.

- Formal entry: the existing IAM binary, `provision-workloads` subcommand, wired only in `cmd/server`. Normal startup never provisions. No public bootstrap RPC.
- An environment owner reviews a non-secret manifest and supplies its exact SHA-256 independently on the command line. The command reads a private file containing an independent `ani_iam_provisioner` DB credential; runtime credentials cannot provision. The fixed environment, trust domain, and CA certificate are independent command inputs. The manifest must match all of them. No credential, key, or bearer token is included in the manifest or receipt.
- X.509 identities use the already accepted exact DNS SAN contract. The manifest pins the actual CA DER SHA-256; the runtime and receiver use that same independently configured CA. Identity is subsequently proved by possession of a CA-issued private key and TLS, never by manifest name alone.
- Manifest v1 contains one UUIDv7 consumption ID, an expiry, and explicit UUIDv7 Workloads, bindings and grants. Only platform Workload creation is supported. No update, enable, revoke, Human creation, Tenant authority, wildcard or overwrite. Allowed targets are explicit IAM ingress RPCs needed by this reference chain and `ani-session-gateway/session.create`; the latter grants no Human subject authority.
- Domain validation is in biz, SQL and explicit transaction are in data, argument/JSON/file validation is in cmd. sqlc generates the business statements. A transaction lock serializes the owner environment. The database permits exactly one bootstrap receipt per environment, regardless of manifest ID or changed trust domain. Canonical intent digest, created identities/grants, one receipt and one attributable security Audit commit atomically. Same manifest ID + same intent returns the original non-secret receipt; different intent is a conflict. A fresh manifest ID with entirely fresh Workload IDs still conflicts once that environment has been initialized, as required by WR-17 section 5. Global unique identities/names reject any attempt to adopt or overwrite an existing registration.
- The DB role is provisioned out of band before migration. It has no schema ownership, superuser, role creation, memberships, UPDATE, DELETE, TRUNCATE, or runtime password access. It can insert only the bootstrap relations and append security Audit; DB triggers additionally deny Human/Tenant-owned insertion by this role and deny forged provisioner attribution from other roles.
- Provisioner audit uses the authenticated DB role and manifest ID with platform boundary, not a fabricated Human/Workload Principal. Existing Human audit actor rules stay intact. The bootstrap receipt and audit have no Tenant because they are platform-owned; tenant-owned relations retain all existing constraints.
- New manifest expiry must be future and no later than 24h after execution time. A completed same-intent retry remains readable after expiry, including after lost response/restart; it does not re-enable any identity or grant. A new expired intent never writes. No automatic retry of an uncertain transaction; explicitly re-run the same reviewed manifest.
- Verification: actual restricted-role PostgreSQL transactions, concurrent duplicate/conflict, second-intent identity collision, schema-level scope rejection, audit-failure rollback, restart/lost-response replay, runtime inability to bootstrap, manifest/CA/environment/unknown-field validation, and unaffected Human/Workload foundation regression. Heavy tests and generation only on ubuntu.
