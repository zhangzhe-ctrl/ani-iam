# WR19 accepted connection authorization

The user's 2026-09-10 decision requires online authorization at admission and ticket redemption, then every 30 seconds. Each check has a 2-second deadline. Revocation, denial, timeout or IAM failure terminates the connection. No cached/offline allow. This document freezes implementation within WR19, not a new general credential platform.

- Initial `VerifyWorkloadInvocation` still requires the current direct caller, WAT and delegation and exact normalized DTO binding. Its reply additionally contains an opaque receiver-bound continuation reference and expiry. A distinct signed JWT type (`ANI-CONTINUATION+JWT`) prevents it from being used as WAT, delegation or Human credential.
- The reference contains the admitted request binding, original direct caller identity and target Grant versions, subject Session/Grant or API Key reference, receiver identity/Binding and verification Grant version. Maximum lifetime is 16 minutes (existing 1-minute ticket plus 15-minute connection limit), capped by the original subject credential expiry. It cannot be renewed or used to create another session. The 5-minute WAT and 60-second delegation bounds are unchanged.
- Only the receiver's own mTLS identity with the exact `/iam.v1.AuthorizationService/VerifySessionContinuation` Grant can submit the reference. IAM validates its type/signature/issuer/audience/expiry, receiver identity, original caller/Binding/target Grant, current subject/Tenant/permission and exact binding. The original request's admission verification Grant must also remain current. This is a current authorization query, not signature-only access. No IAM resource execution ledger is introduced.
- SDK owns reference serialization and online RPC details; business modules never parse tokens. Session stores the SDK's opaque reference encrypted and authenticated with session ID plus owner fingerprint as associated data in the same Redis create as ticket/idempotency. Retries do not replace the original proof; a fresh admission check plus recheck of the original stored proof is required before returning the original ticket.
- A valid ticket is atomically claimed first, then rechecked before WebSocket upgrade or runtime access. Denial consumes/closes that claim and releases its lease, with no runtime opening. This avoids authorizing arbitrary unauthenticated ticket probes. No terminal bytes are processed during reauthorization.
- Claimed Session holds a private, bound recheck function. The connection module checks every 30 seconds, also during runtime establishment, cancels both runtime and transport on failure and releases the Redis lease. All connection modes share this timer; only real container exec is the required successful backend in this ticket.
- Sensitive references are neither public response fields nor logs; safe evidence records only outcomes, fixed input identities, process/fixture IDs and timestamps. Expired references are fail-closed. Reuse of retained K8s fixtures requires fresh short-lived restricted Kubernetes tokens and fresh test identity/data per run.

Exact paths are in the amended IAM and Session implementation scopes. Verification includes expiry beyond creation delegation, request/receiver/type confusion, current state revocation, dependency outage/deadline and recovery, ticket retry/consumption, real stream termination and affected regression gates. Full chain remains `not_verified` until execution proves it.
