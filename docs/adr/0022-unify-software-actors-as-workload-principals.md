# Unify software actors as Workload Principals

ANI IAM has exactly two Principal types: `human` for a natural person and `workload` for a stable software actor. The previous `service` Principal type is removed rather than retained as a compatibility alias. This decision supersedes only the Principal classification in ADR-0018 and incorporates by reference ADR-0018's still-accepted Tenant Access, lifecycle projection, bootstrap-operation, and purpose-specific notification-outbox decisions.

A Workload Principal is not a Pod, process, certificate, API Key, token, deployment, or network location. Its owner is an independent axis: a Tenant-owned Workload represents customer automation and is constrained to one Core-generated Tenant, while a Platform-owned Workload represents an ANI-operated service, Gateway, worker, or control-plane integration. Owner, Identity Binding, Credential, Authority, and per-request execution context are modelled independently so that changing an authentication method does not change the Principal's domain type or silently change its authority.

Within one environment and trust domain, Principal cardinality follows an independently governed security responsibility and revocation lifecycle rather than replica, Pod, endpoint, or rollout count. Replicas, rollouts, and certificate rotations reuse the stable Principal. Producer, consumer, and executor roles of one program may reuse it when they truly share that security and revocation boundary while retaining separate Bindings and Grants; an independently revocable role receives a separate Principal.

Every Workload has an immutable canonical name normalized as `lower(btrim(name))`, with empty names rejected. A Tenant-owned name is unique within its exact Tenant; a Platform-owned name is unique within the IAM environment/trust domain. Disabled Workloads keep the name reserved, so names never become an identity-reuse channel; a mutable display label, if later needed, is a separate non-authoritative attribute.

An active Tenant-owned Workload has exactly one current non-removed Tenant Membership (`active` or `suspended`) for its immutable owner Tenant; a disabled Workload has at most one, and the Membership-removal terminal path has zero. Historical removed rows do not count. Enabling requires an existing matching non-removed Membership or atomically creates a new Membership identity for that owner Tenant; it never revives a removed row or revoked API Key. Tenant authority exists only while the current Membership and its Role Bindings are active; suspension removes authority without changing Principal identity, while removal disables the Workload and irreversibly revokes its API Keys. Its initial credential is an API Key belonging to that Workload, not an independent subject or a snapshot of the Human creator's permissions. A future SPIFFE binding or Workload Access Token does not change this authority source and requires a separately accepted trust policy; a Tenant-owned Workload cannot acquire Platform Membership or Workload Grants.

Platform-owned Workloads do not manufacture Tenant or Platform Memberships. Their runtime identity, Credential and Authority must remain separate, and every synchronous business gRPC/HTTP hop must authenticate its direct caller as a Workload Principal and authorize the exact target without treating an empty or request-supplied Tenant ID as wildcard Authority. On 2026-09-10 the user accepted online IAM verification by Session Gateway (D01), and the combination of Gateway's own Workload identity and target authority with a short IAM-issued delegation credential restricted to the served subject, Tenant, resource and operation (D02 synchronous part). IAM unavailability denies that invocation; there is no offline-allow fallback. The [first-chain contract](../../.scratch/ani-iam-workload-refoundation/evidence/17-freeze-api-replacement-contracts/contracts.md) specifies the finite Gateway-to-Session mapping. Asynchronous Core message provenance remains a separate unaccepted choice in the [current decision register](../../.scratch/ani-iam-workload-refoundation/decisions.md); accepting synchronous delegation does not accept the former full Scope × Evidence matrix.

Every business service-to-service hop keeps the authenticated direct Workload caller distinct from any Human or Tenant Workload being served; the latter cannot substitute for the direct caller's identity or authority. Namespace membership, NetworkPolicy, a request body, a forwarded user token, an ordinary Header, or a shared Secret is never sufficient Workload Identity. The accepted first-chain decision is implemented through its finite contract; other peer/token profiles, streaming revocation timing and health/readiness exceptions require their applicable contracts before use.

Because the project is pre-launch and the user confirmed on 2026-09-09 that there are no immutable external consumers or real IAM data, the target v1 contract and clean schema are refounded in place. The replacement v1 exposes only `human` and `workload`; the removed `service` name and value remain reserved as ordinary Protobuf wire hygiene, not as an accepted value, alias, runtime shim, or compatibility branch. No `service -> workload` mapping, dual write, compatibility view, record-by-record migration, or long-lived dual contract is built. Existing Direct P2 evidence through DP2-10 remains historical evidence only; all affected contracts, generated registries, persistence, and caller integrations must be re-frozen before implementation resumes.

The current [specification](../../.scratch/ani-iam-workload-refoundation/spec.md) and [ticket plan](../../.scratch/ani-iam-workload-refoundation/ticket-plan.md) stage this accepted direction into M1 interface-replacement readiness in an isolated environment and M2 actual replacement. An M1 item freezes its affected artifacts and resolves its applicable open choices; unrelated administration or recovery proposals are not automatically prerequisites for every interface item. M1 does not establish M2 completion or authorize removal of Core's old identity code; frontend integration and that removal follow M1 under their own explicit scope. This staging does not waive the accepted security boundaries above.

## Considered options

- Keep `Service Principal` for Tenant automation and `Workload Principal` for internal runtimes. Rejected because it mixes owner and authentication method into the type and becomes ambiguous when a Tenant workload uses SPIFFE or a Platform workload uses another credential.
- Add a `NonHuman Principal` base with Service and Workload subtypes. Rejected because policies and audits would still branch on the subtype while every caller learns an extra abstraction.
- Use only `Human | Workload`. Accepted because the type answers one stable question—person or software—while orthogonal relations express ownership, authentication, and authority.

## Consequences

- `PRINCIPAL_TYPE_SERVICE` and value `2` are reserved while `PRINCIPAL_TYPE_WORKLOAD` remains value `3`; `ServicePrincipal`, Service Token, related operations, storage names, audit target names, and generated caller registries require a coordinated breaking replacement.
- Tenant and Platform management entrypoints remain separate even though both manage Workload Principals. A Tenant caller must never be able to construct a Platform-owned Workload through a generic CRUD surface.
- Principal type, Workload owner type, and a Tenant owner's Tenant ID are immutable. Human/Workload conversion or owner/Tenant transfer creates a new Principal and explicitly rebuilds intended authority before disabling and revoking the old Principal and Credentials; authority is never changed in place from Membership to Grant or vice versa.
- The IAM runtime needs one deep Workload Authentication module that maps a verified peer or credential to a stable Workload Principal, and one Workload Authorization module that evaluates owner-specific authority without exposing SPIFFE, token, or storage details to callers.
- Gateway-to-Session-Gateway is the first mandatory cross-service reference chain; the same direct-caller and delegated-subject contract applies to all later synchronous business gRPC/HTTP integrations.
- The first chain must deliver reusable, independently versioned caller and receiver Adapters. Ordinary services declare exact operations and retain resource ownership/state checks and business idempotency; they do not replicate credential issuance, verification, delegation or transport trust rules. Generated Proto clients alone do not meet this requirement.
- Contract, migration, runtime/configuration, deployment, ANI registry, and caller changes are separate follow-on work items with fixed artifacts and human checkpoints. This ADR alone authorizes none of those mutations.
- The initial platform-trust bootstrap cannot be modelled as a third Principal or runtime self-registration. The refoundation design plan proposes a narrowly controlled Platform Trust Seed, but its manifest, mechanism and external trust inputs remain pending in the current decision register; the current M1 ticket plan identifies the minimum trust decisions required for each interface slice.
- Audit attribution does not create more Principal types. Successfully authenticated events use a Human/Workload Principal actor; failed authentication and any pre-trust seed event require constrained non-Principal provenance variants. Those variants carry no Authority, and their exact contract remains follow-on work.
