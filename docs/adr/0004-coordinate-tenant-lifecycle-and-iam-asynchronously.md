# Coordinate Tenant Lifecycle and IAM asynchronously

Core Control generates the immutable Tenant ID and moves Tenant Lifecycle to active using only Core-owned Tenant and Quota invariants; it does not wait for IAM administrator creation. Core Control writes lifecycle changes and outbound messages atomically, using separate `TenantLifecycleChanged` and `TenantIAMBootstrapRequested` contracts. IAM consumes the bootstrap contract idempotently and maintains a lifecycle projection for early rejection, while Core and Services still enforce authoritative Lifecycle at the resource boundary.

Tenant IAM Bootstrap is a separate operation from Core tenant provisioning. IAM creates Tenant Access as `bootstrap_pending`; an unknown initial administrator email remains a pending Invitation rather than becoming an unverified active Principal. Tenant Access becomes `active` only when a verified Principal, active Tenant Membership, and active tenant-admin Role Binding are committed together. BOSS reports Core readiness, IAM readiness, and overall tenant operational readiness separately. Disabling a Tenant blocks operations but preserves IAM memberships, role bindings, invitations, and audit history; physical erasure requires a separate purge decision.

Outside the authenticated bootstrap path, a missing Tenant Access row is an IAM readiness failure rather than an authorization denial or evidence that the Core Tenant does not exist. Tenant-scoped operations fail closed with retryable `TENANT_IAM_NOT_READY` semantics, while authentication may still succeed. Recovery replays the original Tenant IAM Bootstrap operation with its original payload; ordinary membership or role requests cannot create Tenant Access, and operators do not repair it by inserting rows directly.

If the original bootstrap operation and payload are unavailable, a platform administrator may initiate a separately identified and audited Recovery Bootstrap with a new idempotency key and an explicitly confirmed initial administrator identity. Recovery does not infer an administrator from current Core or IAM data and does not masquerade as the missing original operation.

Lifecycle projection freshness is not inferred from the age of an individual Tenant row. Each projected Tenant carries a monotonic lifecycle version, while a separate consumer watermark or heartbeat represents the health and progress of the projection pipeline; an unchanged Tenant may remain valid while the pipeline is healthy. Core emits a heartbeat every ten seconds through the same transactional outbox, publisher, stream, and consumer path as lifecycle events. Normal lifecycle propagation has a p99 target of five seconds, and IAM treats the projection pipeline as stale after thirty seconds without progress. A version gap makes only the affected Tenant projection stale and triggers background reconciliation through a service-authenticated, versioned Core REST/OpenAPI snapshot contract; duplicate or older versions are ignored idempotently, and ordinary authorization requests do not query Core synchronously. The IAM service identity is limited to Tenant ID, lifecycle status and version, and snapshot cursor, using TLS and a short-lived audience-restricted service token.

Full projection rebuild obtains a consistent Core snapshot cursor, establishes a durable consumer for messages after that cursor, loads the cursor-bound paginated snapshot, atomically activates the rebuilt projection, and then catches up the buffered increment. It does not stop Core writes or accept a gap between snapshot and subscription.

The bootstrap message handler atomically persists the received operation identity and payload fingerprint before acknowledging delivery, and a durable worker performs the recoverable IAM reconciliation. When the initial administrator is not yet verified, the operation enters the stable, non-error `waiting_for_principal_verification` state without active retries; Invitation acceptance resumes reconciliation and eventually moves it to `succeeded`. An expired Invitation moves the operation to `attention_required`; it may be reissued to the same intended identity under the same operation, while changing that identity requires Recovery Bootstrap approval. Poison messages move to a consumer-specific IAM database DLQ containing the original payload, headers, schema version, event identity, attempt count, and last error. The source message is acknowledged only after DLQ persistence succeeds, and repaired messages replay into the IAM durable worker rather than rebroadcasting the cross-project message. Replay requires the dedicated `iam.dlq.replay` permission and a reason, preserves the original payload, and creates a new attempt linked to the immutable DLQ record.

Recovery Bootstrap requires a dedicated platform permission, recent re-authentication, a reason and external approval or change reference, and immutable audit evidence. The requester and approver are different identities, an approval reference is single-use, and self-approval is forbidden. Approval binds the Tenant ID, intended administrator identity, and request payload hash for one hour; execution requires re-authentication within the preceding fifteen minutes, and any bound-field change requires new approval. Ordinary platform-administrator privileges alone do not grant this capability.

Cross-project delivery is explicitly at least once. Publisher crashes after broker acceptance but before outbox acknowledgement can produce duplicates; IAM removes their business effects using stable event and operation identities, payload fingerprints, lifecycle versions, database uniqueness, and per-Tenant compare-and-swap rather than claiming distributed exactly-once delivery. Different Tenants may reconcile concurrently, while a version gap prevents an out-of-order completion from advancing the affected Tenant until snapshot repair.

Each lifecycle event is a state-carrying fact containing the complete current lifecycle status, version, reason code, and effective time rather than an imperative delta. Core generates a stable event UUID and writes the subject, schema major, payload, aggregate identity and version, retry metadata, error state, and publication state in the same Tenant and Quota transaction; failure to persist the outbox row aborts that business transaction. Publisher failures use exponential backoff. After twenty attempts, the row becomes `attention_required`, remains undelivered and recoverable, raises an alert, and does not block unrelated rows. Recovery requires a dedicated permission and reason, preserves the immutable payload, and records a linked attempt; changing the payload requires a new domain operation.

Lifecycle projection enforcement begins in shadow mode and is compared with authoritative Core decisions. Shadow exit requires at least twenty-four hours of active pre-production real or synthetic lifecycle workload, p99 propagation within five seconds, no unresolved version gaps, no unexplained authorization mismatch, and a successful full projection rebuild. Because the September 30 environment has no real users and is explicitly test-only, one isolated test-Tenant canary may expand directly to all test Tenants after its checkpoint. This shortcut does not define a future production rollout policy. If the shadow exit gate is not met by September 30, the test delivery keeps the projection in shadow, retains authoritative Core and Services Lifecycle guards, and reports IAM early rejection as `not_verified`. Rollback disables only IAM's projection-based early rejection, keeps authoritative guards enabled, and marks the system degraded.

Published outbox rows and raw payloads are retained for thirty days before deletion, with long-lived audit limited to non-PII metadata. Unpublished and `attention_required` rows never expire automatically.
